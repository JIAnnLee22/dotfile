# 代码注释与日志规范

这是一份**指导原则**，而非强制清单。在编写代码时，根据当前项目上下文和代码的重要程度，**自行判断**是否需要添加注释或日志。

核心判断标准：**如果这段代码的逻辑在后续维护时需要额外理解成本，就加注释；如果运行时出问题需要追踪，就加日志。**

## 一、什么时候值得加注释

注释的价值在于解释"**意图和原因**"，不是复述代码做了什么。以下场景通常值得加注释，但最终由你根据实际项目上下文决定：

- **复杂业务逻辑**：为什么这样做而不是那样做？有什么特殊的业务背景？
- **非显而易见的实现选择**：为什么用深拷贝而不是浅拷贝？为什么选这个数据结构？
- **容易踩坑的地方**：边界条件、隐含约束、已知限制
- **外部依赖的假设**：依赖某个 API 的特定行为、某个配置文件的格式约定
- **临时方案**：标注 TODO/FIXME/HACK，说明原因和预期的替换时机

以下情况通常不需要注释（也不绝对，视项目规范而定）：

- 代码本身已经足够清晰表达意图的
- 简单的 CRUD、getter/setter、一眼能看懂的赋值和调用
- 变量名和函数名已经充分说明含义的

### 注释格式参考

不同语言有不同的文档注释习惯。以下为常见语言的参考格式，选用时遵循项目已有的风格即可：

- **Python**: docstring（三引号）
- **TypeScript/JavaScript**: JSDoc
- **Java/Kotlin**: JavaDoc / KDoc
- **Go**: 函数注释以函数名开头
- **Rust**: `///` 文档注释

## 二、什么时候值得加日志

日志的核心目的是**出问题时能快速定位**。判断标准：如果这段逻辑在生产环境出了问题，没有日志的话排查会很困难吗？如果答案是"是"，就加日志。

以下场景**通常**值得加日志，但具体视项目规模和运维需求决定：

- **关键业务操作**（状态变更、数据变更）：出问题需要回溯
- **外部调用**（API、数据库、消息队列）：调用失败时需要知道请求和响应内容
- **异常处理**：不要吞掉异常，至少记录关键信息
- **重要分支逻辑**：走了哪个分支可能影响后续行为

### 日志原则

- **结构化**：优先使用 key=value 或 JSON 格式，方便日志平台检索
- **带上下文**：包含 traceId / requestId / 业务关键 ID
- **脱敏**：不输出密码、手机号、Token 等敏感信息
- **适度**：循环和高频调用中汇总打印，不逐条输出

## 三、执行方式

在编写或修改代码时，**边写边想**：

1. 这段逻辑重要吗？6 个月后别人（或自己）还能一眼看懂吗？→ 决定是否加注释
2. 这段逻辑出问题时能快速定位吗？→ 决定是否加日志
3. 如果加，加多少合适？少即是多，精准优于冗余

**不是每段代码都需要注释和日志。** 一个简单的 5 行工具函数可能完全不需要，一个核心支付逻辑可能需要详细的注释和完整的日志链路。一切取决于项目场景和代码的重要性。
