# 并行子任务

`parallel_tasks` 工具把多个**互不依赖的子任务**派发到隔离的 pi 子进程中并行执行，
全部结束后把结果汇总回当前会话，由你完成整合。

它有两种子任务：

- **只读角色**（`probe` / `analyst` / `verifier` / `reviewer`）：在仓库中调研、定位、核验、审查，不修改任何文件。
- **写角色**（`implementer`）：在**隔离的 git worktree** 中写代码、跑测试，产出 diff 交给你审查后合并。

## 什么时候用

满足**全部**条件才值得并行：

- 拆出来的子任务之间**没有先后依赖**——B 不需要等 A 的结论才能开始。
- 每个子任务都能**脱离当前会话上下文独立理解**。
- 至少有 2 个子任务。只有 1 个时直接自己做，派发反而更慢。

典型触发场景（不限于调研）：

- 用户明确说「同时处理 xx 和 yy」「并行看一下这几处」「这几个文件/模块分别改」。
- 需要在代码库多个互不相关的区域各找一遍（例如同时排查前端调用点和后端实现）。
- 同一个结论需要多个角度交叉验证。
- 面对陌生模块，需要同时摸清若干条独立线索。
- 需要对多块互不相关的代码做独立审查（`reviewer`）。
- 有多个**互不重叠**的文件/功能可以分别独立实现（`implementer`），例如「分别给 A、B 两个模块加各自的单元测试」「分别实现两个互不依赖的 util 函数」。
- 数据量大、需要多处汇总分析时，把不同切片分给多个 `analyst` 并行读。

## 什么时候不要用

- **任务有依赖链**：先定位再分析再改，这是顺序工作，直接做。
- **写任务会改同一批文件**：多个 `implementer` 若改同一文件，合并时必然冲突，这种应该自己顺序改，或只拆一个写任务。
- **任务很小**：一次 grep 就能解决的事，派发的开销远大于收益。
- **子任务描述必须引用当前会话的上下文**才说得清——子进程看不到你的对话历史。

## 可用角色

| 角色 | 类型 | 用途 | 产出 |
|------|------|------|------|
| `probe` | 只读 | 定位取证：找到相关文件、符号、调用点 | `路径:行号` 引用清单 |
| `analyst` | 只读 | 机制分析：读懂某个流程如何工作 | 带证据的机制说明 |
| `verifier` | 只读 | 假设核验：判定一个具体假设是否成立 | 成立 / 不成立 / 证据不足 |
| `reviewer` | 只读 | 代码审查：找出缺陷、风险、改进点 | 分档审查意见 |
| `implementer` | 写 | 独立实现：在隔离 worktree 中写代码、跑测试 | 结论 + diff |

只读角色只能使用 `read`/`grep`/`find`/`ls`/受白名单限制的 `bash`；`implementer` 额外有 `write`/`edit`，
并运行在隔离的 git worktree 中，bash 有危险命令黑名单和越界写入拦截。

## 怎么写子任务描述

子进程**看不到**你的对话历史、看不到其他子任务、也看不到彼此的结论。描述必须自包含：

- 写清楚**范围**：哪个目录、哪些文件、哪个模块。
- 写清楚**判断标准**：什么算找到了，什么算没找到；写任务则说清要改哪个文件、改成什么样、如何验证。
- 给 `verifier` 的必须是**可判定的假设**，不是开放问题。
- 给 `implementer` 的要划清**边界**：只改哪些文件、不要碰什么，避免它越界。

反例（子进程无法理解）：

```
role: analyst
task: 看看刚才说的那个问题在这里是不是也存在
```

正例（自包含）：

```
role: analyst
task: 分析 src/core/session-manager.ts 中 session 条目的持久化流程：
      条目何时写盘、是否有缓冲、进程异常退出时未落盘的条目会怎样。
```

## 整合阶段

子任务全部结束后，结果会连同整合要求一起回到当前会话。你需要：

1. **合并共识**——多个子任务独立得出的一致结论，可信度最高。
2. **处理冲突**——结论矛盾时以有 `路径:行号` 证据的一方为准；无法判定就明确告诉用户存在分歧，不要静默挑一个。
3. **保留存疑项**——子任务标注的「存疑 / 证据不足 / 风险」不要在整合时丢掉。
4. **落地只读结论**——只读子任务不改文件，需要动手改代码时由你在当前会话执行。
5. **审查并应用 diff**——`implementer` 子任务返回的是基于 HEAD 的 diff，尚未落到当前工作区；审查无误后用 `git apply`（或逐文件 edit/write）应用到当前工作区，然后跑测试。多个写任务若改同一文件，先手工消解冲突再应用。
